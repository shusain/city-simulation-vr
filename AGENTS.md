# City Sim VR development instructions

Read `docs/DEVELOPMENT_TASKS.md` first, then the linked Gitea issue and its comments. The Markdown file is only the Active / Next up / TODO index; Gitea owns task scope, plans, status, acceptance and handoffs. Read `docs/DEVELOPMENT_WORKFLOW.md` for process and `docs/DEVELOPMENT_CONTRACTS.md` for shared defaults; `docs/BUGS.md` is only the linked open-bug index; Gitea owns defect reports, investigation, fixes and acceptance. Use `docs/CHANGELOG.md` for completed features and bug fixes and `docs/ENVIRONMENT.md` for the verified toolchain, build/deploy commands and smoke-test regression; do not restart environment setup.

## Working baseline

- Unreal 5.7.4, Meta XR 203.0 (`OculusXR`), Native OpenXR, Android ARM64/Vulkan/ASTC.
- Project: `CitySimVR/CitySimVR.uproject`. The existing VR template is a regression scene.
- Use local development tools for iteration and Drone for final Editor builds/focused test execution and necessary platform playtest candidate packaging; see the workflow below and `docs/DRONE_CI.md`. Local `Tools/Build-QuestSandbox.ps1` is a fallback for a recorded CI gap; `Tools/Deploy-QuestSandbox.ps1` still requires authorized device deployment. Keep the QuestSmokeTest scripts for the preserved VR-template regression.
- The build script applies the tracked Meta compiler fix. Keep it when restoring the ignored vendor plugin.
- Keep target SDK 35 and native API override android-32. Explicit Unreal user SDK settings override environment fallbacks; see `docs/ENVIRONMENT.md` if tools regress.
- The permanent C++ module exists at `CitySimVR/Source/CitySimVR`. Never implement gameplay in generated `Intermediate/Source` files.

## Development approach

- Work on the next dependency-ready task; keep each change focused and independently reviewable. Update its status and evidence before ending a session.
- Plan external asset authoring/review (Blender, SuperCollider, or other suitable tools) separately from Unreal import/material/runtime integration and packaged playtesting. Independent work may proceed in parallel with separate task outputs and nonoverlapping inputs; coordinate shared production files and source/catalog outputs. Finish and identify reviewed source assets before integration, and keep pending physical device observations explicit. See `docs/DEVELOPMENT_WORKFLOW.md` for planning and ownership.
- Keep `docs/DEVELOPMENT_TASKS.md` as a concise linked Active / Next up / TODO list. Maintain detailed feature/asset/validation plans, decisions, evidence, current status and next actions on their Gitea issues. Track concrete defects on their matching Gitea issues with reported/reproduced status, evidence and focused next steps; keep only linked open defects in `docs/BUGS.md` (historical IDs remain references); do not leave a delivered feature open solely for a bug. Record verified completed feature cards/slices and bug fixes with dated evidence in the shared `docs/CHANGELOG.md`, then remove completed work from its active queue. Pending device checks stay active until confirmed; deferred coverage is not a bug or a measured pass. Files in `docs/archive` are historical snapshots, not a second task queue.
- Preserve the smoke-test map. Put new gameplay under `CitySimVR/Source/CitySimVR` and `CitySimVR/Content/CitySim`.
- Author authoritative simulation/commands in C++; use Blueprints for presentation and UI composition. No per-building or per-citizen ticking Actors.
- Extend the existing sandbox and asset pipeline. Avoid new engine versions, plugins, custom shaders, networking, or large framework refactors unless a concrete task needs them.
- Use the defaults in `docs/DEVELOPMENT_WORKFLOW.md` and `docs/DEVELOPMENT_CONTRACTS.md` for routine choices. Record necessary deviations with reasons instead of repeatedly asking for design decisions already covered there.
- Use proportional validation (user2026-10-12, Drone default2026-10-16, PC-first clarification2026-10-18): C++ changes require a Drone Editor build and only the focused checks needed for affected behavior, known defects or concrete integration risks. Package Windows when desktop/PCVR playtest is needed; packaging and human playtest are not required for every feature, issue closure or merge. Reviewed local screenshots/evidence can establish acceptance for simple changes alongside applicable final Drone checks. Batch playtests across multiple merged features when useful. Shared C++/assets alone do not justify Android packaging. Reserve Quest packaging and hands-on PCVR/Quest checks for larger integration milestones with a named VR/mobile risk, UI/input/presentation changes that need headset validation, a concrete platform defect/build risk, or an explicit request/release requirement. Batch periodic Quest checks at useful milestones rather than per feature. Record the reason and affected platform before selecting extra checks; deferred Quest coverage does not block desktop acceptance. Use local builds/tests as needed during iteration; do not duplicate an already sufficient check or run full suites/all-platform builds by default; stop after sufficient evidence. Never claim device rendering or comfort from desktop tests alone.
- Optimize only when absolutely necessary to resolve an observed usability/performance blocker or a demonstrated limit preventing the requested feature. Larger-map work may include one bounded representative usability/performance check and a focused fix if needed; after that, no automatic benchmark, optimization, thermal or capacity-testing program. Formal performance matrices remain deferred until a concrete need or explicit user request. Preserve existing evidence rather than regenerating it.
- Early-development policy (user2026-10-12): prioritize fast, focused iteration. Backwards compatibility for old city files/assets is optional, not a release gate; breaking formats/IDs/assets is acceptable when it makes the current work simpler. Document breaking changes for testers; add migrations only when inexpensive or specifically requested. Preserve user files on disk unless their removal is authorized. Keep current-version save/load and valid current assets working; do not clear caches or reinstall tools as a first troubleshooting step.
- Local Git/LFS is initialized. Check current state before using Git and preserve unrelated working-tree changes. The user authorizes scoped branch pushes and draft PRs for the requested work's CI validation as described below; unrelated publication remains outside that scope. Do not force-push shared history.

## Drone builds, tests and PR queue — user directive 2026-10-16

- For requested implementation work, prepare a focused commit, push a scoped branch and create or update its draft Gitea PR against `main` before playtest so Drone can validate it. This is standing user authorization; do not ask again merely to push the scoped change or open its validation PR. This directive supersedes older instructions/skill sequencing that postponed PR creation until after playtest. Gameplay acceptance, review/checks and the normal authorized merge closeout still apply before merging; opening a validation PR is not acceptance or release approval.
- Prefer an isolated branch/worktree based on current remote `main`. Inspect the complete PR diff and required Git/LFS inputs; exclude unrelated local commits, dirty source/assets, player files and secrets. Include only necessary, identified prerequisites in the authorized scope. Never pull/reset/rebase another chat's active primary checkout just to obtain the CI baseline. CI builds the pushed revision, not the current dirty development tree.
- Let `windows-checks` compile Editor with warnings as errors and run the exact tests in `Tools/CI/Tests.txt`. Select the affected exact cases in the PR; the three starter tests are not coverage for every feature. Use local builds, focused tests, imports, debugging and captures for normal development iteration; no CI-gap exception is needed. Coordinate actual shared file conflicts and avoid replaying already sufficient checks. Run final Editor/focused test validation through Drone on the submitted revision.
- Drone capacity1 queues CI jobs in isolated workspaces. Submit scoped jobs without a manual native claim, workstation process check, CI lock or worker hold/resume handoff. Local development may continue alongside CI. Coordinate only actual shared file/output conflicts or observed resource contention; preserve other tasks and player sessions. Keep the existing worker enabled; do not start duplicate runners or jobs. Record PR/build URL, SHA, status and next action; queued/running is not a pass.
- For ordinary playtest delivery, promote the intended tested build to `windows-playtest` by default. Select `quest-playtest` only for a recorded Quest validation need above, and `both-playtest` only when both candidates are needed for that milestone; never use it automatically after each change. Verify the actual candidate receipt, applicable packaged smoke, ZIP/hash and startup evidence, then request human playtest of that exact revision. CI candidates stay separate from the maintained game and real player profiles. Maintained-package promotion, manual input/headset observations, release and device deployment retain their existing gates. Quest candidates require signed APK/ARM64/API/embedded-cook verification; headset behavior stays unconfirmed until observed. Hosted artifact downloads are not supplied by this pipeline.
- Record actual Drone results and remaining checks on the Gitea issue and in its evidence records. Leave the existing worker enabled for future jobs; no CI native claim is required. Documentation-only instruction changes need relevant static review, not a manual Unreal rebuild.
