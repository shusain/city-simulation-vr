# Metric time windows (#281)

The authoritative fixed-step clock uses150 steps per day,25 days per calendar month and12 months per year. At1x a step lasts2.4 seconds; speed changes wall-clock delivery only. FixedStepsPerMonth, LastBilledMonthId, LastSettledMonthId, report Months/MonthId and several ledger LastMonth fields are legacy names for daily settlement intervals. This change preserves their timing and serialized names.

| Metrics | Meaning in a raw daily record | Monthly/annual aggregation |
| --- | --- | --- |
| Income, upkeep due, wages due/paid, goods produced/purchased/exported | Actual amount recorded at that daily settlement; event amounts, not rates | Sum observed daily amounts once; never multiply by steps, speed or missing days |
| Borrowing, principal/interest paid/accrued, policy due/administration/grants/recipient payments | Actual daily ledger amounts | Sum observed amounts; unfunded program count sums program-days |
| Population, employment, education, homelessness, treasury, inventory, utility demand/capacity, pollution, detention, illness/care/leave, treatment capacity, waste stored/cargo/piles, happiness and concerns, loan balance/arrears | Daily closing snapshot | Latest retained daily close; not a time average |
| Arsons, arrests, recoveries, generated/collected/disposed/recycled/overflow waste, migration counts/fees and departure money | Cumulative counters to date | Latest cumulative reading; never sum lifetime counters |
| Quarterly mean mood | Daily total happiness divided by daily resident count | Sum happiness points and resident observations over every retained day in quarter, then divide once; a resident-day weighted average of daily samples, not continuous within-day sampling |

Monthly totals combine days1–25,26–50 and so on. Annual totals combine300 days. Coverage counts actual retained daily records, including partial first/last months; missing days are not extrapolated. A month touched by one retained day counts as an observed month but is not a complete month. Internal annual summaries retain both month and day coverage; quarterly completeness requires all75 daily observations. Closing concerns/census still describe the latest daily close. Missing sentiment on any observed day prevents claiming an available quarter-wide mean. Other lifetime totals remain explicitly labelled to date; quarterly movement subtracts the preceding retained closing counter or reports unavailable. If the first retained record starts after day1 with no baseline, movement is unavailable even within calendar month1.

Raw daily facts remain the persisted authority. Rollups are derived and do not change save schema. Restore neither recaptures an already recorded daily settlement nor resets pending event counters. No retiming of citizen travel, wages, purchases, production, services or billing; this is an aggregation/report correction. Existing monthly/yearly history is recalculated on load from retained facts; old missing facts are not recreated.

Budget/needs projections retain daily settlement amounts and now say /day and LAST DAY, matching the already daily building upkeep labels.

Concrete pre-fix mismatches: daily event sums labelled dollars/month or units/month; annual UI attempted to replace /day and retained the erroneous monthly rate; quarterly mood discarded all but month-end samples; annual sentiment availability used the last month even when an earlier observed day was missing. Existing flow summation and closing/cumulative snapshot rules were already correct and are retained.

Validation: CitySim.Reports.TimeScaleAggregation checks known301-day event totals, month/year boundaries, partial retention, daily mood weighting, missing coverage, clock equivalence at1x/3x/5x and current-format mid-period save/load continuity. Existing daily-calendar, settled-history, news capture/editorial and report-panel cases provide focused integration coverage. #279 separately owns the legacy distribution-smoke fixture and unsafe empty-history indexing; its80-step assumption is not a production aggregation result. No rates are annualized and no per-second normalization is introduced without an actual rate metric.

## Report period selector

Hourly, Daily, Weekly and Monthly are directly selectable, with Monthly the default. A week is five calendar-aligned days: days1-5 are Week1,6-10 Week2; five weeks fit each25-day month. Daily charts use saved daily rows; weekly/monthly charts sum observed event amounts and retain the latest daily closing snapshot/cumulative reading. Each daily-derived period shows actual observed days out of1/5/25. Partial periods are not filled or extrapolated. Changing period retains metric/category and selects its latest recorded period; previous/next navigate within that period. Annual derived helpers remain available internally for quarter/year computations and historical tests, but Annual is absent from the visible selector.

## Real hourly observations

The authoritative subsystem records at each completed game-hour boundary.150 fixed steps/day cannot divide evenly into24 hours: boundaries are ceil(hour*150/24), first at step7 (~16.8 seconds at1x), then13,19,25. Catchup and speed changes still visit every fixed step; pause records nothing. Snapshot metrics are the actual closing readings, cumulative metrics are actual counters to date. Purchases use differences in the completed-arrival purchase counter; exports use differences in completed-export counters, carrying the daily reset correctly. They are never daily totals divided by24. Daily ledger flows (tax, upkeep, wages, production, loans, policies) remain settled daily and appear once in the hour crossing midnight; other hourly rows contain zero for these flows. There is no change to financial settlement or citizen/travel timing.

Retain120 hourly observations (latest five days) separately from3000 daily rows. Hourly windows record actual start/end steps. A city without hourly history primes the baseline on load and records only new observations; its first hour can be partial and is labelled accordingly. No historical hours are synthesized from daily facts. The optional hourlyReports section preserves observation baseline counters and windows in the current save schema, including mid-hour loads; old files without the section keep their daily history. Validation rejects malformed windows and impossible purchase baselines.

Hourly has an independent empty state explaining the next completed game hour. Daily/weekly/monthly charts still first appear after the first daily settlement at midnight. The chart window displays24 observations and supports previous/next navigation through retained hours. Monthly remains the default on opening Reports.
